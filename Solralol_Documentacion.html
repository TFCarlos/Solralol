Snapshot de arquitectura

Solralol

Panel de control, overlay, historial, inspector y análisis postpartida para League of Legends, desarrollado con Python y PySide6. Lee datos locales de una partida activa, graba su propia telemetría de la partida, la sincroniza con Riot API (Match‑V5) al terminar, y ofrece un diálogo de análisis LIVE comparando cada calle. También consulta el historial oficial bajo demanda y ofrece un visor de análisis web por campeón.

PySide6

Interfaz, layouts, señales, hilos, diálogos y visor web integrado.

Live Client + Riot

Datos en vivo desde League local, grabación de sesión y sincronización con Match‑V5.

Data Dragon

Catálogo, iconos y caché local de campeones y objetos.

El export de código inicial no incluía app/ui/main_window.py (la ventana principal actual, importada por main.py). Ese archivo se recibió después y todo este documento se ha revisado y corregido contra su código real, línea a línea, en lo que respecta a navegación, botones de análisis y cableado de señales/hilos. Requisitos e inicio

  • Windows con League of Legends instalado y una partida activa, incluida la herramienta de práctica, para los datos Live Client.
  • Python 3.10 o superior y un entorno virtual recomendado (activate_env.bat activa .venv).
  • Dependencias principales (requirements.txt): requests, urllib3, PySide6, keyboard.
  • Para el visor integrado de Análisis y los diálogos de análisis debe estar disponible PySide6.QtWebEngineWidgets / PySide6.QtWebEngineCore.
  • Una Riot API key propia para el historial y la sincronización postpartida (se guarda desde Ajustes).

La API local de League usa un certificado HTTPS autofirmado. Por ello GameService, riot_live.py y app/services/riotlive.py hacen peticiones con verify=False, y silencian urllib3.exceptions.InsecureRequestWarning al importarse. La Riot API real (RiotApiService, SettingsService.validate_riot_api_key) usa requests con verificación de certificado normal (no se desactiva verify).

Flujo de datos

1. Panel en vivo

League local→ GameService→ LiveDataWorker→ MainWindow→ ChampionCard / Overlay

League expone datos de la partida en local. GameService los convierte en un snapshot compacto. El worker los consulta en un QThread; la interfaz recibe el snapshot mediante señales Qt y actualiza widgets exclusivamente desde el hilo principal.

{
  "game_mode": "PRACTICETOOL",
  "game_status": "IN_PROGRESS",
  "game_time": 1234.5,
  "champion_id": "Varus",
  "item_ids": [1055, 3006],
  "local_player": {...},
  "local_team": "ORDER",
  "enemies": [...],
  "all_players": [...],
  "local_live_stats": {...},
  "game_events": [...]
}

2. Grabación local + sincronización con Riot (nuevo)

LiveDataWorker→ LiveMatchTracker→ live_match_sessions.json→ PostgameSyncWorker→ LiveMatchAnalysisDialog

Cada read_snapshot() de LiveDataWorker actualiza un LiveMatchTracker, que va guardando en memoria la sesión de la partida en curso y la emite (live_analysis_ready) para análisis LIVE. Al terminar la partida, la sesión se cierra y se persiste en disco. Después (por acción del usuario — ver botones Analizar / Re‑analizar / Ver), PostgameSyncWorker intenta emparejarla con la partida real de Riot para completarla con datos oficiales, y el resultado se muestra en LiveMatchAnalysisDialog.

3. Historial oficial (bajo demanda)

Riot ID→ RiotApiService→ MatchHistoryWorker→ MatchHistoryCache→ Historial / Inspector

El flujo de historial es independiente del timer Live Client y de la sincronización postpartida. Solo se ejecuta por acción manual del usuario y reutiliza la caché para no repetir descargas de partidas ya conocidas.

GameService

app/services/game_service.py encapsula la comunicación con la API local. No contiene widgets ni código de presentación. Silencia InsecureRequestWarning a nivel de módulo porque siempre usa verify=False.

MétodoFunción
request_data(endpoint)GET genérico a BASE_URL/endpoint con timeout=2 y verify=False; propaga requests.RequestException.
is_in_game()Devuelve True si /gamestats responde con un diccionario; captura errores de red.
get_game_snapshot()Combina /allgamedata y /eventdata, identifica al jugador local (por summonerName o riotId coincidiendo con activePlayer, con fallback al primer jugador no-bot), separa enemigos por equipo y devuelve el diccionario normalizado que consume el resto de la app (ver ejemplo JSON en Flujo de datos).
Si /eventdata falla o no es un diccionario, game_events queda como lista vacía en vez de romper el snapshot completo: el fallo de un endpoint secundario nunca debe tumbar el panel en vivo.

LiveDataWorker

app/services/live_data_worker.py — es el worker realmente usado por app/ui/control_window.py (y, con toda probabilidad, por main_window.py). Vive en un QThread propio.

SeñalCuándo se emite
snapshot_ready(object)Cada lectura correcta de GameService.get_game_snapshot(). Lleva el snapshot normalizado para refrescar tarjetas/overlay.
read_failed(str)Cuando no hay partida activa o la lectura falla; mensaje ya listo para mostrar en la UI.
live_analysis_ready(object)Nuevo. Tras cada snapshot correcto, entrega la sesión LIVE actual del LiveMatchTracker (con source="live_client_data_api", live=True y final_sync.status="live") para alimentar LiveMatchAnalysisDialog mientras la partida sigue en curso.
live_analysis_failed(str)Cuando la lectura lanza una excepción no controlada.

Ciclo de vida de una partida dentro del worker

  1. read_snapshot() pide un snapshot a GameService.
  2. Si es None (no hay partida): cierra cualquier sesión abierta (_finish_tracking), resetea was_in_game y la "firma" de la partida, y emite read_failed.
  3. Si hay snapshot: calcula una firma de partida (game_mode | riotId | summonerName | local_team). Si la firma cambia respecto a la anterior y el tiempo de partida es menor a 10 s, entiende que ha empezado una partida nueva: cierra (si procede) la sesión anterior y arranca (tracker.start) una nueva. En caso contrario, simplemente actualiza (tracker.update) la sesión en curso.
  4. Emite snapshot_ready para la UI y, a continuación, live_analysis_ready con la sesión LIVE (si el tracker ya tiene una).
Archivo casi idéntico sin usar: app/services/live_data_worker_live_analysis.py define otra clase LiveDataWorker con la misma lógica (nombres de señal ligeramente distintos: snapshot_failed en vez de read_failed). No lo importa ningún archivo del proyecto. Ver Archivos duplicados / sin uso.

LiveMatchTracker nuevo

app/services/live_match_tracker.py es el componente central de la nueva función de análisis: convierte snapshots sueltos de la Live Client Data API en una sesión de partida completa y persistente, con series temporales por jugador y eventos de objetivos.

Constantes clave

  • SAMPLE_INTERVAL_SECONDS = 2.0: no se guarda un punto nuevo si no han pasado al menos 2 s de tiempo de partida desde el último (salvo force=True, usado al arrancar).
  • MAX_SAVED_SESSIONS = 50: al persistir, sólo se conservan las 50 sesiones más recientes en ~/.solralol/live_match_sessions.json.
  • ROLES = (TOP, JUNGLE, MIDDLE, BOTTOM, UTILITY) y ROLE_ALIASES normalizan variantes de texto (BOT, ADC, SUP, etc.) a esos cinco valores.
  • OBJECTIVE_EVENTS traduce los tipos de evento de la Live Client Data API (dragonkill, baronkill, heraldkill, turretkilled, inhibkilled) a claves internas (dragon, baron, rift_herald, tower, inhibitor) con etiqueta en español.

Métodos principales

MétodoFunción
is_tracking (propiedad)True mientras hay una sesión abierta en memoria.
start(snapshot)Crea una sesión nueva (ver esquema) con session_id único (fecha + campeón), estado inicial final_sync.status = "live_only", y llama a update(snapshot, force=True) para el primer punto.
update(snapshot, force=False)Si no ha pasado el intervalo mínimo y no es forzado, no hace nada. Si toca muestrear: indexa jugadores, registra eventos exactos, añade un punto de snapshot y detecta cambios relevantes por jugador (objetos nuevos, etc.).
finish()Cierra la sesión activa, calcula el final_scoreboard a partir del último punto conocido de cada jugador, quita campos internos de trabajo (seen_event_ids, last_player_state), la añade a las sesiones guardadas y persiste el fichero (recortando a MAX_SAVED_SESSIONS). Devuelve la sesión completa o None si no había nada en curso.
get_live_session()Devuelve una copia profunda de la sesión en curso (o None), para poder emitirla por señal sin riesgo de mutación concurrente.
load_saved_sessions()Lee y devuelve la lista de sesiones guardadas en ~/.solralol/live_match_sessions.json; si el archivo no existe o está corrupto, devuelve [].
delete_saved_session(session_id)Elimina una sesión guardada por su id y reescribe el fichero.

Cómo se identifica y clasifica a cada jugador

  • _identity(player): usa riotId si existe, si no summonerName, si no compone riotIdGameName#riotIdTagLine.
  • _player_key(player, index): clave estable "{team}:{identidad}" en minúsculas, con player-{index} como último recurso si no hay identidad.
  • _role(player): usa la posición reportada por la API y la normaliza con ROLE_ALIASES; si la posición es NONE y el jugador lleva Ignite/Smite entre sus hechizos, infiere JUNGLE (heurística ya documentada en la versión anterior de este documento).
  • lane_matchups: para cada rol, guarda la clave del primer aliado y del primer enemigo detectados en ese rol; es lo que usa LiveMatchAnalysisDialog para enfrentar "tu jugador de la calle" contra su rival.

Estimación de oro y estadísticas en vivo

_estimate_gold usa el oro real (current_gold) cuando está disponible (jugador local, vía activePlayer.championStats); para el resto de jugadores, estima con una fórmula simple: valor del inventario + 300 por kill + 75 por asistencia + 20 por creep. _stats intenta encontrar daño a campeones/estructuras, daño recibido, curación y visión, mirando primero local_live_stats (solo disponible para el jugador local) y si no, player["stats"]/player["scores"]/el propio diccionario del jugador, probando varios nombres de campo posibles (por ejemplo totalDamageToChampions o damageToChampions).

Estos valores LIVE son estimaciones. Cuando la sesión se sincroniza con Riot (ver Sincronización postpartida), el final_scoreboard se sustituye por datos exactos de Match‑V5.

ChampionCard

app/ui/champion_card.py construye una tarjeta (QFrame) por jugador. Usa player["team"] para elegir el color de fondo (no la condición de "es el jugador local"): QRadialGradient dibuja un brillo azul para ORDER y rojo para CHAOS, manteniendo la parte superior más oscura. Incluye cabecera (icono de campeón + nombre), fila de estadísticas y una etiqueta de resumen de runas.

Inventario

app/ui/inventory.py siempre debe devolver un QWidget (nunca None, o falla addWidget en el layout padre). Los slots 0–5 son inventario normal y el slot 6 es el trinket. Incluye get_player_role, is_boots/find_boots (para tratar especialmente el calzado) y create_item_icon/create_item_slots para construir los iconos con fallback cuando no hay asset local.

Overlay

app/ui/overlay_window.py (OverlayWindow, hereda de QMainWindow) es una ventana flotante puramente visual: muestra datos resumidos ya calculados por la app, permite ajustar opacidad (set_overlay_opacity), arrastrar la ventana (mousePressEvent/mouseMoveEvent/mouseReleaseEvent) y activar el modo "click‑through" (set_click_through). No hace ninguna petición HTTP ni consulta la API por su cuenta: recibe los datos ya procesados vía update_data.

Estilos (QSS)

app/ui/styles.py centraliza la hoja de estilos Qt del panel (colores, tipografías, formas de tarjetas). Recordatorio importante: QSS no soporta text-shadow; si se necesita un efecto de sombra en texto hay que simularlo con capas o con QGraphicsDropShadowEffect desde Python, nunca con esa propiedad CSS.

RiotApiService y ajustes

app/services/settings_service.py (SettingsService) administra ~/.solralol/settings.json: inicializa self.settings_path en __init__ (requisito obligatorio, ver Diagnóstico), y ofrece load(), save(), save_riot_api_key(), clear_riot_api_key() y validate_riot_api_key() (esta última hace una petición real a lol/status/v4/platform-data en euw1 para comprobar que la clave es válida, distinguiendo 200/401/403/429/otros). La Riot API key nunca debe guardarse dentro de match_history_cache.json.

Buscador e historial — regla crítica de rate limit confirmado

No es una pestaña propia: vive dentro de Inicio, en la tarjeta "Actividad reciente" (create_home_page). Componentes reales: botón "Actualizar historial" (refresh_history_button → request_match_history), campos riot_game_name_input ("Nombre de Riot ID") y riot_tag_line_input ("TAG", máx. 5 caracteres), y una etiqueta de estado history_status.

No añadir sondeo de Riot API al poll_timer de Live Client. El historial se consulta solo al pulsar "Actualizar historial" (request_match_history); no hay ninguna llamada automática a Riot al arrancar la app ni al cambiar de pestaña.
  • El historial por defecto consulta 5 partidas (count en MatchHistoryWorker.load_history).
  • MatchHistoryCache (app/services/match_history_cache.py) persiste en ~/.solralol/match_history_cache.json: cuentas (account_key/get_account/save_account), resúmenes/detalles por match_id (get_match/save_match/get_matches) y el cooldown de rate limit (rate_limit_remaining_seconds, activate_rate_limit_cooldown, clear_rate_limit_cooldown).
  • Una partida detallada nunca debería descargarse dos veces: siempre comprobar la caché antes de llamar a Riot.
  • Ante HTTP 429: show_match_detail_error(message, retry_after) deshabilita refresh_history_button y lo reactiva automáticamente pasados retry_after segundos con QTimer.singleShot(retry_after * 1000, self.enable_history_refresh), mostrando en history_status cuánto falta.
  • MatchHistoryWorker (QThread, history_thread) expone load_history() y load_match_detail(), con señales history_ready → receive_match_history, history_failed → show_match_history_error, detail_ready → open_match_inspector y detail_failed → show_match_detail_error.
  • Al recibir el detalle (open_match_inspector) se abre directamente MatchInspectorDialog(match_detail, item_catalog, data_dragon_assets, self) como modal (.exec()).

Página de Ajustes confirmado

create_settings_page: campo de Riot API key (api_key_input, modo contraseña, placeholder RGAPI-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx) con dos botones, "Guardar y comprobar" (save_and_validate_api_key) y "Eliminar clave" (clear_api_key), más los campos de Riot ID y regiones (riot_account_region/riot_platform_region, guardados con save_riot_id).

save_and_validate_api_key llama a SettingsService.validate_riot_api_key(api_key) de forma síncrona, en el hilo de interfaz (no pasa por ningún QThread). Esa llamada hace una petición HTTP real a lol/status/v4/platform-data en euw1, así que mientras Riot responde la ventana puede quedarse sin refrescar unos instantes. Es una excepción puntual a la regla general "toda petición HTTP bloqueante va en un worker" — aceptable porque es una acción explícita y poco frecuente del usuario (guardar la clave), pero conviene tenerlo en cuenta si algún día se nota un pequeño parón al pulsar "Guardar y comprobar".

Si la clave es válida, se guarda con settings_service.save_riot_api_key(api_key) y se refleja en self.riot_api_key; si no, se limpia con clear_riot_api_key(). El estado visual (api_key_status, con la propiedad QSS state en checking/valid/invalid) se repinta manualmente con unpolish()/polish() para forzar que Qt vuelva a aplicar el estilo tras cambiar la propiedad dinámica.

Sincronización postpartida nuevo

app/services/postgame_sync_service.py (PostgameSyncService) es el corazón de la nueva función de análisis con Riot API: coge una sesión LIVE ya terminada (grabada por LiveMatchTracker) y la completa con los datos oficiales de esa misma partida en los servidores de Riot.

Constantes

  • MAX_CANDIDATES = 10: número máximo de partidas recientes del jugador que se comprueban como posible coincidencia.
  • START_TOLERANCE_SECONDS = 12 * 60: diferencia máxima admitida entre la hora de inicio local y la de Riot.
  • DURATION_TOLERANCE_SECONDS = 4 * 60: diferencia máxima admitida entre duración local y duración según Riot.

sync_session(session) — algoritmo paso a paso

  1. Comprobación previa (_can_sync): hace falta API key, game_name, tag_line y que la sesión tenga local_player_key. Si falta algo, se devuelve la sesión sin tocar con final_sync.status = "live_only" y el mensaje "Sin Riot ID o API key: se conserva telemetría LIVE."
  2. Resolución de cuenta: RiotApiService.get_account_by_riot_id obtiene el PUUID.
  3. Candidatas: get_match_ids(puuid, count=MAX_CANDIDATES) trae hasta 10 IDs de partidas recientes.
  4. Puntuación de cada candidata (_candidate_score):
    • Se descarta si el campeón jugado en esa partida (según Match‑V5) no coincide con session["champion_name"].
    • Se calcula la diferencia entre la hora de inicio local (session["started_at"]) y gameStartTimestamp/gameCreation de Riot; se descarta si supera START_TOLERANCE_SECONDS.
    • Se calcula la diferencia entre session["duration"] y gameDuration; se descarta si hay duración local y la diferencia supera DURATION_TOLERANCE_SECONDS.
    • La puntuación final es diferencia_de_inicio + 2 × diferencia_de_duración (cuanto menor, mejor).
  5. Selección: se elige la candidata con menor puntuación. Si ninguna pasa los filtros, la sesión queda en estado "pending" ("Esperando a que Riot procese la partida.").
  6. Fusión (_merge_riot_data): con la partida elegida, se descarga también su timeline y se hace lo siguiente:
    • Se mapea cada participantId de Riot a la clave interna de jugador de la sesión, primero por Riot ID normalizado y, si no hay coincidencia, por par (campeón, equipo).
    • Se rellena meta["final"] de cada jugador emparejado con _official_player_stats (ver más abajo) y se marca meta["win"].
    • session["final_scoreboard"] pasa a ser el marcador oficial (antes era una estimación LIVE).
    • session["winning_team"] se calcula a partir de teamId/win del jugador local.
    • Se guardan session["riot_match"] (respuesta cruda de Match‑V5) y session["riot_timeline"] (respuesta cruda de la timeline).
    • session["official_events"] sustituye a los eventos estimados en vivo si Riot ha devuelto alguno (session["events"] = official_events or events).
    • session["postgame"] = True y session["final_sync"] pasa a {"status": "synced", "match_id": ..., "synced_at": ..., "source": "riot_match_v5", "message": "Partida sincronizada con Riot Match-V5."}.
  7. Errores: un RiotApiError con status_code 404 o 429 se traduce a estado "pending" (tiene sentido reintentar); cualquier otro RiotApiError, o cualquier excepción inesperada, se traduce a estado "failed" con el mensaje de error.

_official_player_stats(participant) — qué datos oficiales se guardan por jugador

KDA (kills, deaths, assists), CS (cs_minions, cs_jungle, cs_total), level, oro (gold_earned, gold_spent), daño (a campeones, estructuras, objetivos, y recibido), utilidad/visión (healing, healing_from_teammates, vision_score, wards_placed, wards_killed, control_wards_purchased, time_cc_dealt), build final (hasta 7 item{N} distintos de 0), runas y sub‑estilos (perk0..5, stat_perk_0..2), hechizos de invocador (spell1_id, spell2_id) y win.

PostgameSyncWorker

app/services/postgame_sync_worker.py ejecuta todo lo anterior en un QThread. Su slot sync_session(session, api_key, game_name, tag_line, account_region, platform_region) crea internamente un RiotApiService y un PostgameSyncService, y emite:

  • sync_ready(dict) — la sesión actualizada (haya quedado synced, pending, failed o live_only: el worker no filtra por estado, simplemente devuelve lo que sync_session haya calculado).
  • sync_failed(str) — sólo ante una excepción no controlada al construir los servicios o llamar a sync_session (no es lo mismo que un estado "failed" dentro de la sesión, que sí se emite por sync_ready).
El worker actual incluye varias líneas print("[WORKER] ...") de depuración en cada paso (creación de servicios, inicio y fin de la sincronización, estado final). Son útiles para depurar mientras se termina de conectar la función a la interfaz, pero conviene revisarlas antes de una versión "final" de cara al usuario.

Comportamiento verificado línea a línea contra app/ui/main_window.py (métodos create_saved_game_row, request_saved_session_sync, request_resync_session, open_saved_game_analysis).

Correspondencia con la terminología de la petición original ("Analizar" / "Re-analizar" / "Ver"):

"Analizar" → botón "Buscar Riot" → request_saved_session_sync(session_id)

  1. Si postgame_sync_in_progress es True, no hace nada (evita lanzar dos sincronizaciones a la vez).
  2. Busca la sesión por session_id en live_match_tracker.load_saved_sessions().
  3. Si el game_mode es PRACTICETOOL, PRACTICE, TUTORIAL, CUSTOM o CUSTOM_GAME, marca la sesión como live_only con el mensaje "No disponible en Riot Match-V5: las partidas de práctica, tutorial y personalizadas conservan telemetría LIVE local." y no llama a Riot.
  4. Si no hay riot_api_key, o falta el nombre/tag del Riot ID en Ajustes, marca la sesión como failed con un mensaje pidiendo configurarlos.
  5. Si todo está listo: guarda pending_postgame_session_id = session_id, marca el estado como pending ("Buscando detalle y timeline en Riot…"), refresca la lista (refresh_saved_games) y llama a start_postgame_sync(session_id).
  6. start_postgame_sync vuelve a leer la sesión de disco (para trabajar con el estado pending recién guardado, no con una copia antigua) y emite la señal postgame_sync_requested(session, riot_api_key, game_name, tag_line, riot_account_region, riot_platform_region), que PostgameSyncWorker recibe en su propio QThread y procesa con PostgameSyncService.sync_session(...) (ver Sincronización postpartida).
  7. La respuesta llega por sync_ready → receive_postgame_sync (sustituye la sesión en disco por la versión devuelta y refresca la lista) o por sync_failed → receive_postgame_sync_error (marca la sesión como failed con el mensaje de error, conservando la telemetría LIVE intacta).

"Re-analizar" → botón "Re-sincronizar" → request_resync_session(session_id)

Solo visible cuando final_sync.status == "synced". Resetea manualmente el estado de sincronización de la sesión guardada:

session["final_sync"] = {
    "status": "live_only",
    "match_id": None,
    "synced_at": None,
    "source": "live_client_data_api",
    "message": "Pendiente de re-sincronización.",
}
session.pop("official_events", None)

Guarda ese cambio directamente en disco (live_match_tracker._save_sessions(sessions)) y a continuación llama a request_saved_session_sync(session_id): es decir, "Re-sincronizar" es literalmente "olvida la sincronización anterior y vuelve a pulsar Buscar Riot".

"Ver" → botón "Abrir análisis" → open_saved_game_analysis(session)

Siempre visible, en cualquier estado. No llama a Riot para nada: simplemente construye y muestra el diálogo con la sesión tal cual está guardada en ese momento.

Un cuarto botón: "Abrir análisis LIVE" (partida en curso)

En la pestaña Partida en vivo, open_live_analysis_button permanece deshabilitado hasta que llega la primera sesión LIVE (receive_live_analysis, conectada a LiveDataWorker.live_analysis_ready). open_live_analysis() reutiliza el diálogo si ya está abierto (show(), raise_(), activateWindow(), update_session(session)) o crea uno nuevo y lo conecta a finished para limpiar la referencia al cerrarse. Mientras la partida sigue en curso, cada sesión LIVE nueva (una por segundo, junto al snapshot del panel) se reenvía automáticamente al diálogo si está abierto, así que se actualiza solo.

Sincronización automática al terminar la partida

Cuando MainWindow detecta que la partida ha terminado, cierra la sesión (live_match_tracker.finish()) y llama a schedule_postgame_sync(session): marca el estado como pending ("Esperando a que Riot procese la partida…") y programa, con QTimer.singleShot(20_000, ...), una primera llamada a start_postgame_sync veinte segundos después — así la primera sincronización ocurre sola, sin que haga falta pulsar "Buscar Riot" la primera vez. Si Riot todavía no tiene la partida procesada en ese momento, la sesión queda en pending y es cuando tiene sentido volver a pulsar el botón manualmente más tarde.

Diálogo de análisis LIVE nuevo

app/services/data_dragon_assets.py (DataDragonAssetService)Servicio Qt (QObject) que descarga imágenes (retratos de campeón, iconos de objeto) de forma asíncrona con QNetworkAccessManager, las cachea en ~/.solralol/ddragon y las entrega como QPixmap vía la señal image_ready o directamente sobre un QLabel con set_label_image.Diálogos Qt: MatchInspectorDialog, LiveMatchAnalysisDialog.

Reglas de DataDragonAssetService ya documentadas y verificadas contra el código:

  • Se crea una sola vez (previsiblemente en MainWindow) y se pasa como parámetro a los diálogos que la necesiten; no debe instanciarse un servicio nuevo por jugador ni por partida (cada instancia mantiene su propio caché en memoria de campeones/objetos y su propio QNetworkAccessManager).
  • Los campeones requieren resolver el ID interno de Data Dragon a partir del nombre visible mediante champion.json (ejemplos ya conocidos: Kha'Zix → Khazix, Wukong → MonkeyKing).
  • Los objetos se identifican por ID numérico; el ID 0 (slot vacío) se omite al renderizar, y cualquier fallo de descarga cae a un icono de respaldo en vez de dejar el hueco vacío o lanzar una excepción.
  • La versión de Data Dragon usada por este servicio está fijada en el propio archivo (self.version = "15.16.1"), independiente de la versión que main.py obtiene dinámicamente al arrancar con data_dragon.load_item_catalog(). Conviene tenerlo en cuenta si un parche nuevo cambia iconos: hay que actualizar esta constante además del catálogo de objetos.

Pestaña Análisis (visor web) confirmado

Página 1 de la navegación (create_analysis_page): análisis externo por campeón/rol/rango/región, distinto del análisis LIVE/postpartida de las secciones anteriores. Incluye:

  • Campo de texto "CAMPEÓN" (analysis_champion_input, placeholder "Ej.: Mordekaiser"; Enter también dispara la carga).
  • QComboBox "ROL": Top / Jungla / Mid / ADC / Support (top, jungle, middle, adc, support).
  • QComboBox "RANGO": desde "Todos los rangos" hasta Challenger, pasando por Hierro+, Bronce+, Plata+, Oro+, Platino+, Esmeralda+, Diamante+, Master+ y Grandmaster+.
  • QComboBox "REGIÓN": Europa Oeste, Europa Este, Norteamérica, Corea, Brasil, Latinoamérica Norte/Sur, Oceanía, Japón, Turquía, Rusia.
  • Botón "Cargar análisis" (load_analysis_button).
  • Selector de fuente: botones LoLalytics (seleccionado por defecto), U.GG y LeagueOfGraphs (select_analysis_source).
  • Botón "Bloqueador: SÍ" (adblock_button, marcado por defecto) para activar/desactivar el bloqueador de anuncios de la sección siguiente.
  • QWebEngineView (analysis_web_view, altura mínima 620 px) con una página QuietWebEnginePage propia.
  • Botones "Recargar" (reload_analysis_button, conectado directamente a analysis_web_view.reload) y "Abrir en navegador" (open_external_button).

Preferencias que se guardan en settings.json vía save_analysis_preferences: analysis_champion, analysis_role, analysis_rank, analysis_region.

load_selected_analysis() normaliza el nombre del campeón a un "slug" (minúsculas, sin espacios, sin comillas simples ni puntos) y construye la URL exacta según la fuente elegida (analysis_values() / load_selected_analysis):

No cargar estas webs por sondeo periódico ni durante una partida activa. La carga solo ocurre al pulsar "Cargar análisis", al presionar Enter en el campo de campeón, o al pulsar "Abrir en navegador" sin haber cargado nada todavía.

Visor y bloqueador confirmado

AdBlockInterceptor (clase definida directamente en main_window.py) hereda de QWebEngineUrlRequestInterceptor y bloquea peticiones del visor de Análisis por dos vías, ambas comprobaciones rápidas en memoria (sin red ni disco):

  • BLOCKED_DOMAINS: una lista fija de 27 dominios conocidos de publicidad/analítica (doubleclick.net, googlesyndication.com, google-analytics.com, googletagmanager.com, amazon-adsystem.com, adnxs.com, taboola.com, outbrain.com, criteo.com/.net, pubmatic.com, rubiconproject.com, openx.net, moatads.com, scorecardresearch.com, quantserve.com, hotjar.com, facebook.net, connect.facebook.net, entre otros): si el host de la petición contiene alguno, se bloquea con info.block(True).
  • BLOCKED_URL_PARTS: fragmentos de ruta/URL sospechosos (/ads/, /adserver/, /advert/, /advertising/, /banner/, /banners/, /promo/, doubleclick, google_ads, googleads, googlesyndication, adservice, adnxs, taboola, outbrain): si la URL completa (en minúsculas) contiene alguno, también se bloquea.

QuietWebEnginePage (también en main_window.py) silencia en la consola de desarrollador tres mensajes concretos y ya identificados como ruido inofensivo de proveedores externos (fun-hooks:, el aviso de inicialización de la integración de Facebook, firstPartyData); cualquier otro mensaje de consola se reenvía sin cambios al comportamiento por defecto de Qt.

Puntos de diseño a respetar si se toca este código:

  • La referencia al interceptor se guarda en self.analysis_adblocker: si se dejara de guardar (por ejemplo, pasándolo como valor anónimo sin asignar), Python podría recolectarlo como basura y QWebEngineView dejaría de aplicar el bloqueo sin avisar.
  • El interceptor se instala una sola vez, sobre el profile de la página del visor: analysis_web_view.page().profile().setUrlRequestInterceptor(self.analysis_adblocker).
  • El botón "Bloqueador: SÍ"/"Bloqueador: NO" (toggle_analysis_adblock) permite desactivarlo si una web concreta deja de funcionar correctamente con el bloqueo activo.
  • Solo afecta al visor integrado de la pestaña Análisis; no toca ninguna petición de la Live Client Data API ni de la Riot API.

Hilos y señales

MainWindow crea y arranca tres QThread en su constructor, cada uno con su worker movido a él con moveToThread:

HiloWorkerSeñal de entrada (hacia el worker)Señales de salida (hacia MainWindow)
worker_threadLiveDataWorkersnapshot_requested → read_snapshot (disparada cada 1000 ms por poll_timer)snapshot_ready → receive_snapshot; live_analysis_ready → receive_live_analysis; read_failed → show_read_error
history_threadMatchHistoryWorkerhistory_requested → load_history; match_detail_requested → load_match_detailhistory_ready → receive_match_history; history_failed → show_match_history_error; detail_ready → open_match_inspector; detail_failed → show_match_detail_error
postgame_sync_threadPostgameSyncWorkerpostgame_sync_requested → sync_sessionsync_ready → receive_postgame_sync; sync_failed → receive_postgame_sync_error

Todas las señales que cruzan de un hilo a otro llevan tipos serializables sencillos (dict, str, int), nunca widgets de Qt: los widgets solo se tocan desde el hilo principal, dentro de los métodos receptores (receive_snapshot, receive_live_analysis, receive_postgame_sync, etc.).

MainWindow.closeEvent para los tres hilos con el mismo patrón: quit(), después wait(5000) y, si no ha terminado, terminate() + wait(2000). También detiene poll_timer y cierra el overlay. Nota menor: el bloque de cierre de postgame_sync_thread tiene una indentación ligeramente distinta a los otros dos (el wait(5000) final no queda anidado dentro del if isRunning()), aunque no es un fallo funcional porque QThread.wait() devuelve True de inmediato si el hilo ya ha terminado.

Limitaciones y reglas

  • La Live Client Data API solo existe mientras hay una partida (o herramienta de práctica) activa; fuera de eso, GameService.is_in_game() devuelve False y la pestaña "Partida en vivo" permanece deshabilitada.
  • La sincronización con Riot solo tiene sentido para partidas de cola pública: las de práctica, tutorial y personalizadas no existen en Match‑V5, así que request_saved_session_sync las descarta explícitamente antes de gastar una llamada a la API.
  • Los valores LIVE (oro, daño, etc.) de LiveMatchTracker son estimaciones hasta que la sesión se sincroniza; solo entonces final_scoreboard pasa a ser el marcador oficial de Riot.
  • La sincronización postpartida depende de tener configurados a la vez: Riot API key válida (Ajustes) y Riot ID completo (nombre + tag, en Inicio). Si falta cualquiera de los dos, la sesión se queda en live_only/failed con un mensaje explicando qué falta.
  • Rate limit de Riot: cooldown local de 120 s si no hay cabecera Retry-After, respetando siempre esa cabecera cuando Riot la envía.
  • DataDragonAssetService tiene fijada su propia versión de Data Dragon (15.16.1 en el código analizado) independientemente de la versión que main.py detecta dinámicamente al arrancar; si Riot publica un parche nuevo con iconos distintos, hay que actualizar esa constante a mano.
  • MAX_SAVED_SESSIONS = 50 en LiveMatchTracker: solo se conservan las 50 partidas grabadas más recientes; las más antiguas se descartan al persistir.

Próximas mejoras

  • Unificar los clientes "LiveClient" duplicados. Hay tres implementaciones distintas de un cliente para la Live Client Data API (app/services/game_service.py en uso, y riot_live.py/app/services/riotlive.py huérfanas): sería más fácil de mantener reescribir debug_cs.py y debug_enemy_runes.py para que usen GameService y borrar los dos clientes duplicados.
  • Revisar los print("[WORKER] ...") de depuración en postgame_sync_worker.py antes de una versión "final" de cara al usuario, o sustituirlos por logging con un nivel configurable.
  • Implementar o retirar el logro "Roamer". AWARD_LABELS en live_analysis_models_and_calculator.py reserva la clave "roamer", pero calculate_achievements nunca la asigna todavía.
  • Mover la validación de la API key a un worker. save_and_validate_api_key hace una petición HTTP síncrona en el hilo de interfaz; sería más consistente con el resto de la app moverla a un QThread corto o reutilizar PostgameSyncWorker/uno nuevo dedicado.
  • Actualizar DataDragonAssetService.version dinámicamente a partir de la versión que ya detecta main.py al arrancar, en vez de mantenerla como constante fija dentro del propio servicio.
  • Retirar o archivar app/ui/control_window.py. Confirmado como código muerto de una arquitectura anterior (con un bug real de closeEvent fuera de la clase); no aporta nada y puede confundir a quien lea el proyecto por primera vez.
  • Reescribir reorganize_project.ps1 o borrarlo. Ya no refleja la estructura real del proyecto (le faltan la mayoría de servicios y diálogos actuales).

Para la IA

Si en el futuro se pide ayuda a una IA (incluido Claude) para seguir desarrollando Solralol, conviene que tenga en cuenta:

  • La ventana principal real es app/ui/main_window.py (MainWindow). app/ui/control_window.py (SolralolWindow) es una arquitectura anterior, confirmada como no usada: no hay que "arreglarla" ni asumir que sigue viva.
  • Antes de dar por hecho que un archivo "no se usa", comprobar con grep -rn "nombre_del_archivo\|NombreDeClase" --include=*.py . desde la raíz del proyecto, igual que se ha hecho para este documento.
  • Los tres estados de final_sync.status relevantes para partidas guardadas son live_only, pending, failed y synced; el estado live es exclusivo de la sesión en curso emitida por LiveDataWorker.live_analysis_ready, no se persiste en live_match_sessions.json.
  • Cualquier nueva llamada a la Riot API debe ir en un QThread propio (o en uno de los tres ya existentes si encaja), nunca directamente en un método de MainWindow llamado desde un botón, salvo que sea una excepción tan puntual y justificada como validate_riot_api_key.
  • No introducir sondeo periódico de Riot API: el único QTimer recurrente debe seguir siendo poll_timer, dedicado exclusivamente a la Live Client Data API local.
  • Antes de tocar LiveMatchTracker, PostgameSyncService o live_analysis_models_and_calculator.py, revisar el esquema de sesión completo: son muchos campos interdependientes (snapshots, eventos, lane_matchups, final_scoreboard, final_sync) y es fácil romper alguno sin darse cuenta.
