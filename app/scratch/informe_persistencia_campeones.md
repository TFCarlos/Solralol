# Persistencia local de campeones — 5 de octubre de 2026

1. **Usos anteriores reemplazados.** El archivo encontrado era `data/champions_strict.json`, en plural; no existía el singular. Se sustituyeron la carga inicial, el editor y la recarga tras actualización de `local_analysis_dialog.py`; el lector/escritor de `ChampionScraperService.actualizar_todo`; la carga de perfiles de `DraftAnalyzerService`; `load_knowledge` de recomendaciones live; `_load_champions`/`_save_champions` de `WinrateCalculatorService`; y la escritura de `data/generate_strict_data.py`. Las referencias documentales del README quedan pendientes de autorización, conforme a AGENTS.md; este trabajo no modificó los cambios previos del README.

2. **Formato elegido: JSON por campeón.** El almacén antiguo ocupaba 1.574.429 bytes, con 173 perfiles. La carpeta original mezclaba tres matrices y 170 documentos estáticos, sumando 2.978.051 bytes. Su mayor matriz, de 50.423 bytes, se deserializaba en 0,41 ms de mediana antes del cambio. El nuevo almacén completo ocupa 1.137.431 bytes. No se necesitan dependencias adicionales.

3. **Comparación de formatos.** Con el mismo contenido y JSON compacto, SQLite con clave primaria `(champion, role, rank)` consultó en 0,15 ms y ocupó 1.216.512 bytes; JSON consultó en 0,44 ms con caché. La diferencia de unas tres décimas de milisegundo no afecta al coste dominante de Qt. Las actualizaciones autorizadas reemplazan un campeón completo, no filas aisladas: JSON simplifica inspección, copia y mantenimiento. Un documento sintético de 85 combinaciones, de 1.045.250 bytes, se deserializó en 8,78 ms, se consultó con caché en 0,26 ms y se escribió con fsync y validación en 23,50 ms. SQLite ofrece mejores actualizaciones parciales, consultas cruzadas y transacciones entre campeones, capacidades que este flujo no necesita. Otros formatos binarios o comprimidos no justifican nuevas dependencias o menor legibilidad con estos tamaños.

4. **Esquema resultante.** Cada documento contiene `schema_version: 2`, `champion`, `profile`, `ranks`, `updated_at`, `source`, `catalog_version`, `update_status` y `coverage`. Una generación remota añade `source_versions` con los parches efectivamente descargados de U.GG. `ranks[rango][línea]` contiene estadísticas y secciones de análisis, recomendaciones precalculadas, `generated_at` y `sample_size` cuando se conoce. El resumen `__lane_stats__` pertenece al rango. Las generaciones nuevas eliminan el resumen repetido en cada variante y las runas duplicadas. Los datos globales se guardan una vez; los recursos gráficos se mantienen como archivos estáticos. No se persiste estado de la vista.

5. **Rutas.** Análisis en `data/champion_data/<identificador_normalizado>.json`, por ejemplo `aatrox.json`. Metadatos de Data Dragon en `data/champion_metadata/`; habilidades en `data/champion_abilities/`. `_paths.DATA_DIR` sigue resolviendo la ubicación escribible en el ejecutable empaquetado. `.gitignore` permite incluir los nuevos documentos de análisis y excluye temporales y cachés estáticas.

6. **Consulta.** `RepositorioCampeones.consultar(campeon, linea, rango)` accede al archivo del campeón y a dos claves de diccionario. No enumera campeones. Copia únicamente el perfil y la combinación solicitados al consumir datos cacheados. La UI conserva su cola Qt y descarta resultados de generaciones de selección obsoletas; se retiró el retardo fijo de 120 ms.

9. **Ausencias y fallos.** Se distinguen `NO_LOCAL_DATA`, `NO_SOURCE_DATA`, `UNSUPPORTED`, `UPDATE_FAILED`, `CORRUPTED_DATA` y `SCHEMA_MISMATCH`, además de datos disponibles. `coverage: partial` identifica datos migrados; una generación completa sin muestra permite distinguir ausencia de fuente. Un fallo conserva las secciones válidas anteriores y registra el intento. La UI oculta el análisis de otra selección y muestra un mensaje español con «Actualizar campeón» disponible. Nunca descarga automáticamente por ausencia local.

10. **Integridad y atomicidad.** Se validan identidad, versión, perfil global, rangos, líneas, campos esenciales, contenedores de enfrentamientos y recomendaciones. La serialización rechaza números no finitos. Se escribe un temporal único en la misma carpeta, se hace flush/fsync y se ejecuta `os.replace`. Los lectores solo ven el documento anterior o el nuevo; los temporales se eliminan ante fallo. La cancelación no publica una matriz parcial. Se conservan los éxitos de otros campeones si falla una fuente o un guardado.

Los bytes de recursos se comparten mediante la caché existente de hasta 1.024 referencias. La actualización manual recrea el servicio y limpia resúmenes de líneas.
